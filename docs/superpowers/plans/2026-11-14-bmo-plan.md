# BMO Plan — Canvas-First Editor UI, Plugins, and Integration

> **Execution control:** `docs/superpowers/plans/2026-11-14-phasing-plan.md` is the one-phase master plan; this document keeps the detailed task steps.

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn the native engine lab into BMO: a canvas-first editor with one floating tool dock, peek/hide chrome, searchable commands, first-party plugin panels, focused source files, and a clean path to replacing Studio in the shipping app.

**Architecture:** Keep the existing `EngineDocument` and Skia/Filament renderer. Replace the current pile of top bars, object bars, and inspector sheet with one `EngineShellState` reducer and one shell composition. On compact widths, panels are bottom sheets; on expanded widths they are edge panels. Plugins are compiled-in `EnginePlugin` implementations hosted in the same panel surface, one at a time, with a hideable session. After the UI and device gate pass, promote the existing Gradle review build to the release build, route the editor to the engine, migrate saved looks, remove Studio, and produce a signed APK.

**Tech Stack:** Kotlin 2.0.21, Compose BOM `2025.02.00`, Compose Material 2 with custom tokens, SceneView 2.3.0 / Filament 1.56, Robolectric 4.14.1, Roborazzi 1.44.0, Android `org.json`.

**Spec:** `NATIVE_EDITOR_V2.md` (especially Tasks 9–11), `tools/engine-spike/PLAN.md` §Canvas-first, `tools/engine-spike/README.md`, and the BMO decisions in this document. This plan supersedes the UI portions of `NATIVE_EDITOR_V2.md` Tasks 7–8 and keeps its integration/ship intent.

## Global Constraints

- Offline only: no account, no sync, no runtime network dependency.
- BMO v1 plugins are **compiled-in first-party plugins**. Do not add a WebView, JavaScript runtime, downloaded APK/DEX, or third-party code loading. The plugin contract is designed so a later runtime can be added without changing the panel UI.
- One editor at a time; do not ship Studio and the engine as two editors.
- No permanent chrome bands. The default composition is the artboard plus floating controls; a fixed full-width bar is a regression.
- One active panel at a time: Layers, Inspector, Commands, or Plugins.
- One active plugin at a time. Hiding a plugin hides its panel but keeps its session; closing it discards the session.
- Keep Kotlin 2.0.21, Compose BOM `2025.02.00`, Compose Material 2, SceneView 2.3.0 and Filament 1.56. No silent dependency upgrade.
- Keep the engine package `app.add.engine` until integration; do not add Filament to the shipping sources before the integration tasks.
- Preserve the ADD palette and typography. Do not introduce Material dynamic colour or a default Material visual language.
- Every interactive target is at least 48 dp and has a content description or visible label.
- Respect the system animation scale; reduced motion removes non-essential motion.
- No visual claim without a reviewed capture. No device claim without a device check.
- Existing engine tests stay green. Baseline before this plan: **166 tests, 0 failures, 0 errors, 0 skipped**; **14 chrome goldens match**.
- Never silently discard a saved look. A field that cannot be migrated is recorded in `FINAL-TEST.md`.

## Review Focus

1. **Canvas obstruction:** hiding chrome must not hide the only way back; peeking, restoring, opening a panel, and dismissing it must never trap the reader or leave an invisible touch target over the artboard.
2. **Plugin lifecycle:** hiding a plugin must preserve its state, closing must discard it, switching plugins must stop the previous one, and a plugin action must be undoable.
3. **Touch arbitration:** canvas drags, pinch/zoom, 3D orbit, text fields, plugin panels, and panel drag-to-dismiss must not steal each other's gestures.
4. **State restoration:** rotation or process death with a panel open, a plugin running, or chrome hidden must return to a usable editor, not a blank or locked screen.
5. **Responsive panels:** compact phones use one bottom sheet; expanded tablets use edge panels; resizing across the breakpoint must not leave two copies of a panel or lose the selection.

## BMO UI analysis

### What Figma actually does

Figma's current UI is the strongest reference because it has already tested canvas-first chrome at scale.

- **Three detached regions, not one app frame:** navigation panel left, toolbar bottom, properties panel right, canvas between them ([Figma right sidebar](https://help.figma.com/hc/en-us/articles/360039832014-Design-prototype-and-explore-layer-properties-in-the-right-sidebar), [left sidebar](https://help.figma.com/hc/en-us/articles/360039831974-View-layers-and-pages-in-the-left-sidebar)).
- **The toolbar is floating at the bottom in UI3** and was explicitly moved there to free canvas space ([Navigating UI3](https://help.figma.com/hc/en-us/articles/23954856027159-Navigating-UI3)).
- **Floating panels were a failed experiment.** Figma moved from floating panels back to docked panels because floating panels cramped the canvas, made designs peek out from behind them, moved rulers away from the work, and slowed people down. Floating survives only for Minimize UI, FigJam, Slides, and bottom toolbars ([Figma on Figma, Oct 2024](https://www.figma.com/blog/our-approach-to-designing-ui3)).
- **Two hiding levels:** Minimize UI collapses the navigation and sidebars but leaves the toolbar; Hide UI removes everything. Selecting an object in Minimize UI can auto-expand the right panel and collapse it on deselect ([Hide or minimize the UI](https://help.figma.com/hc/en-us/articles/41414918021271-Hide-or-minimize-the-UI)).
- **Search is the escape hatch:** Actions (`Ctrl/Cmd K`) is the single place for tools, commands, asset search, and plugins ([Actions menu](https://help.figma.com/hc/en-us/articles/23570416033943-Use-the-actions-menu-in-Figma-Design)).
- **Plugins have one doorway and one active process:** the Tools tab and Actions menu surface plugins; only one plugin runs at a time; a plugin modal is an iframe that can hide, move, resize, and keep running ([Use plugins in files](https://help.figma.com/hc/en-us/articles/360042532714-Use-plugins-in-files), [`figma.showUI`](https://developers.figma.com/docs/plugins/api/properties/figma-showui), [`figma.ui`](https://developers.figma.com/docs/plugins/api/figma-ui/)). Dev Mode intentionally docks plugin UI into the Inspect panel so it does not obscure the canvas ([Working in Dev Mode](https://developers.figma.com/docs/plugins/working-in-dev-mode)).

### What the other editors teach

- **Penpot** keeps a numbered, always-present chrome and hides panel groups through its main menu. Its toolbar uses flyouts for secondary tools, and its plugin manager is a single modal doorway with an `Open` action ([interface tour](https://help.penpot.app/user-guide/first-steps/the-interface), [plugins](https://help.penpot.dev/user-guide/plugins-integrations)). Lesson: one plugin doorway and progressive disclosure beat a row of plugin buttons.
- **Excalidraw** is canvas-dominant with one dockable sidebar that closes on outside click and a `zenMode` that removes chrome ([Sidebar](https://docs.excalidraw.com/docs/@excalidraw/excalidraw/api/children-components/sidebar), [UIOptions](https://docs.excalidraw.com/docs/@excalidraw/excalidraw/api/props/ui-options)). Lesson: one side panel at a time, with an explicit zen/canvas mode.
- **Canva** renders apps in a side panel but also surfaces intent-based app actions contextually on a selected object ([Apps inside Canva](https://www.canva.dev/docs/apps/apps-inside-canva), [Intents](https://www.canva.dev/docs/apps/intents/)). Lesson: a plugin can have a contextual action without requiring the reader to open a plugin menu first.

### BMO decisions

1. **Artboard first.** The shell is a transparent overlay on top of the stage, not a column of bars above and below it.
2. **Floating tool dock only.** The bottom dock floats. Properties and layers do not float in the middle of the canvas; on phones they are sheets, on tablets they are edge panels. This deliberately follows Figma's retreat from floating property panels.
3. **Three chrome levels:** `Full` (dock + page chip + selection rail), `Peek` (page chip only), `Canvas` (no chrome except a 48 dp restore handle at the top edge).
4. **One surface at a time.** `Layers`, `Inspector`, `Commands`, and `Plugins` are mutually exclusive. Opening one closes the other without losing the document selection.
5. **Search is a first-class control.** BMO Actions/Commands is the equivalent of Figma's Actions menu: every command, including plugin commands, is reachable from one search field.
6. **Plugins are panels, not dialogs over the canvas.** A plugin takes over the inspector surface, with a running chip and a hide action. Hiding preserves the plugin session; closing ends it. A plugin can also contribute commands to BMO Actions and a contextual "run" action for a selection.
7. **One plugin at a time.** This is a deliberate constraint from Figma's model: parallel plugin panels would recreate the occlusion problem BMO is removing.
8. **No plugin marketplace in v1.** The app is offline and does not load untrusted code. BMO ships a plugin contract plus first-party plugins; the UI is ready for more later.

### Task 1: Add the shell state machine

**Files:**
- Create: `tools/engine-spike/app/src/main/java/app/add/engine/EngineShellState.kt`
- Test: `tools/engine-spike/app/src/test/java/app/add/engine/EngineShellStateTest.kt`

**Interfaces:**
- Consumes: nothing.
- Produces:
  ```kotlin
  enum class ChromeMode { Full, Peek, Canvas }
  enum class EngineSurface { None, Layers, Inspector, Commands, Plugins }
  data class EngineShellState(
      val chrome: ChromeMode = ChromeMode.Full,
      val surface: EngineSurface = EngineSurface.None,
      val pluginId: String? = null,
  )
  sealed interface ShellEvent {
      data object CanvasTouched : ShellEvent
      data object PeekTapped : ShellEvent
      data object ToggleChrome : ShellEvent
      data class Open(val surface: EngineSurface) : ShellEvent
      data object Dismiss : ShellEvent
      data class OpenPlugin(val id: String) : ShellEvent
      data object HidePlugin : ShellEvent
      data object ClosePlugin : ShellEvent
  }
  fun EngineShellState.reduce(event: ShellEvent): EngineShellState
  ```

**Rules to implement and pin in tests:**
- `CanvasTouched` closes an open surface; otherwise `Full` becomes `Peek`. It never enters `Canvas` by itself.
- `PeekTapped` restores `Full`.
- `ToggleChrome` cycles `Full → Peek → Canvas → Full` and closes any surface while doing so.
- `Open` sets the one surface and forces `Full`; opening `Plugins` does not clear `pluginId`.
- `Dismiss` clears the surface but leaves `chrome` alone.
- `OpenPlugin(id)` sets `pluginId`, opens `Plugins`, and forces `Full`.
- `HidePlugin` clears the surface but keeps `pluginId`.
- `ClosePlugin` clears `pluginId` and leaves `Plugins` if it was the active surface; opening another surface later shows the shelf.
